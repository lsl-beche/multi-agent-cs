# CSagent L2 标准企业级落地路线图

> 目标版本：v1.0  
> 目标等级：L2 标准企业级生产系统  
> 目标环境：阿里云（主区域，双可用区）  
> 合规基线：PIPL + 网络安全等级保护三级自查  
> 更新日期：2026-08-30

## 1. 结论

CSagent 当前具备完整的电商、多 Agent 客服、商城和管理后台功能，但从工程成熟度看仍处于“可演示原型/生产化前期”阶段，尚未达到标准企业级。

本方案的目标是把项目建设为：

- 支持 10 万 DAU、峰值 1000 QPS、2000 个 WebSocket 连接；
- 月度可用性 99.9%；
- 完整安全、权限、审计、隐私、合规能力；
- 可水平扩容、可审计、可回滚、可运维、可演进的单地域生产系统；
- 保留模块化单体架构，不提前拆分微服务、不建设多地域容灾、不覆盖多租户 SaaS。

预计实施周期约 16～18 周，4～5 人团队。若团队 2～3 人，预计 9～12 个月。

## 2. L2 企业级定义与验收指标

### 2.1 业务与非功能目标

| 类别 | 目标 |
|---|---|
| 用户规模 | 10 万 DAU |
| 峰值请求 | 1000 QPS（读为主），100 写入 QPS |
| 客服连接 | 2000 并发 WebSocket，跨实例接管成功率 100% |
| 下单并发 | 500 并发创建订单，零超卖、零重复核销优惠券 |
| 可用性 | 月度 99.9% |
| 响应时间 | 普通 API P95 < 300ms、P99 < 800ms；客服 P95 < 500ms |
| 错误率 | 系统错误率 < 0.1%，业务重试可恢复 |
| RPO | ≤ 5 分钟 |
| RTO | ≤ 30 分钟 |
| 数据库变更 | 所有 schema 变更通过 Alembic，支持 upgrade/downgrade |
| 测试 | 服务层覆盖率 ≥ 70%，关键 API 有集成测试，预发布有压力测试 |
| 安全 | 高危漏洞清零，权限矩阵回归通过，PII 加密，审计日志完整 |
| 合规 | PIPL、数据安全法、网络安全法等要求可审计；等保三级自查通过 |
| 部署 | 多副本、滚动发布、蓝绿/金丝雀、一键回滚、Secret 外置 |

### 2.2 明确不做的事（第一阶段）

- 不拆微服务：保留模块化单体 + outbox 事件；
- 不做多地域容灾：先做单地域双可用区高可用；
- 不做多租户 SaaS：先面向单商家/单主体；
- 不自训练大模型：使用云端模型 + 本地降级；
- 不同时接入多种支付/物流渠道：先接一种真实支付、一种真实物流，其余保留沙箱；
- 不做移动端原生 App：通过 H5/Web 和现有小型程序入口扩展。

## 5. 技术实施方案

### 5.1 数据库与数据模型

#### 目标

- 全链路异步数据库访问，事件循环零阻塞；
- 金额使用 `Decimal`，API 层统一转 `float`；
- 订单、库存等核心表使用 version/条件更新；
- 所有 schema 变更走 Alembic；
- 建立备份、恢复、数据迁移和数据保留策略。

#### 关键工作

1. `app/core/db.py`：改为 `create_async_engine` + `async_sessionmaker`；
2. `app/api/deps.py`：`get_db` 改为异步依赖；
3. 12 个 service 和 21 个路由逐模块切换；
4. `Decimal` 类型迁移：`app/models/tables.py` + Alembic；
5. `Inventory.version` + `orders.version` 乐观锁；
6. `updated_at` 增加 `onupdate`；
7. SQLAlchemy 连接池指标接入 Prometheus；
8. 数据库连接使用内网 + 白名单，生产禁止公网直连；
9. 建立 `alembic upgrade head` 和 `alembic downgrade -1` 验证；
10. RDS 自动备份、PITR、每周恢复演练。

### 5.2 事务、事件与一致性

#### 目标

订单、库存、优惠券、支付、退款、物流之间形成可对账、可重试、可补偿的一致性闭环。

#### 关键设计

- 核心写操作统一放入 Service，路由只做参数校验和响应；
- 库存使用条件 `UPDATE`，返回受影响行数；
- 订单创建单事务：地址校验 -> 原子扣库存 -> 条件核销优惠券 -> 建单 -> 清购物车 -> 写 outbox；
- 支付回调幂等：`payment_no + trade_no` 唯一约束 + 状态机；
- 退款闭环：审核 -> 支付状态 -> 库存回补 -> outbox 事件 -> 财务对账；
- 物流：发货记录 + 轨迹同步 + 状态迁移；
- outbox 表：`id, aggregate_type, aggregate_id, event_type, payload, status, created_at, published_at`；
- outbox worker：轮询 + 幂等 + 失败重试 + 死信；
- 双阶段发布前，禁止生产接受真实支付。

### 5.3 安全与权限

#### 认证

- access token 15 分钟，refresh token 7 天；
- refresh token 轮换 + 复用检测 + 吊销；
- 登录失败计数、账户/IP 锁定；
- 密码策略：长度、复杂度、历史、强制改密；
- WebSocket 使用查询参数或握手头传 token，并在 accept 前校验；
- C 端、客服、管理端身份分离。

#### 授权

- 权限源：数据库 `roles / permissions / role_permissions`；
- JWT 只携带 `sub/role` 或最小权限快照；
- 管理接口统一 `Depends(require_permission(...))`，fail-closed；
- 对象级授权：订单、会话、工单、地址、优惠券按 `user_id` 校验；
- 权限矩阵：4 角色 × 全部管理接口，自动化回归；
- 角色/权限变更后 Redis 缓存即时失效。

#### 数据安全

- 手机号、地址、对话、身份证等 PII 分类；
- 静态加密：RDS/Tair/OSS 服务端加密；
- 字段级加密：`FIELD_ENCRYPTION_KEY` + Fernet；
- 日志脱敏：手机、邮箱、地址、对话摘要；
- 审计日志：谁、何时、何地、什么操作、结果；
- 敏感操作二次确认/风控；
- 安全响应头：HSTS、X-Frame-Options、CSP、X-Content-Type-Options。

### 5.4 PIPL 与等保三级自查

#### PIPL 控制清单

- 处理目的、方式、范围明确；
- 隐私政策、用户协议、授权同意；
- 敏感信息单独同意；
- 数据最小化与分类分级；
- 数据主体权利：查询、复制、更正、删除、撤回同意；
- 数据处置期限与到期删除；
- 委托处理/供应商协议；
- 个人信息保护影响评估（PIA）；
- 跨境传输评估（若涉及）；
- 安全事件报告和应急响应；
- 日志、审计、数据删除演练。

#### 等保三级自查重点

- 安全管理制度与组织；
- 人员安全、培训、离岗管理；
- 物理与环境安全；
- 通信网络、区域边界；
- 计算环境：身份鉴别、访问控制、安全审计、恶意代码防范、可信验证；
- 应用系统：安全审计、数据完整性/保密性/备份恢复；
- 集中安全管理和安全运维；
- 系统变更、漏洞、补丁、应急、演练、恢复；
- 第三方渗透测试与外协管理。

### 5.5 可观测性

| 指标 | 示例 |
|---|---|
| 黄金指标 | 请求量、P50/P95/P99、错误率、饱和度 |
| 业务指标 | 下单量、支付成功率、退款率、转人工率、意图分布 |
| AI 指标 | LLM 调用量、token 成本、缓存命中率、超时率 |
| 资源指标 | CPU、内存、DB max_connections、Redis 内存 |
| WebSocket | 在线连接数、跨实例消息成功率 |

日志：

- JSON 结构化日志；
- `trace_id / request_id / user_id / session_id`；
- 日志分级、脱敏、采样、保留 180 天；
- 禁止打印密码、token、PII。

告警：

- 错误率 > 0.1%；
- P99 > 800ms；
- 数据库连接池耗尽；
- Redis 内存/连接异常；
- 支付回调失败、outbox 堆积、退款失败；
- 4xx/5xx 比例、磁盘、证书到期。

### 5.6 部署、扩展与回滚

#### 多实例

- API 无状态化；
- Session/会话状态放 Redis；
- WebSocket 通过 Redis Pub/Sub 跨实例投递；
- HPA 按 CPU、内存、自定义业务指标扩缩；
- Pod 反亲和、PDB、资源限额；
- 日志/指标采集为 sidecar 或 DaemonSet；
- 数据库使用连接池、读副本、慢查询监控；
- Redis 使用 Cluster 或主从 + 哨兵。

#### 发布

- 镜像 tag = git SHA；
- ACR 镜像仓库；
- ArgoCD/GitOps 或云效流水线；
- staging 自动部署，生产手动审批；
- 蓝绿/金丝雀：先 5% 流量，再 50%，再全量；
- 数据库迁移采用 expand/migrate/contract，兼容新旧版本；
- 一键回滚：保留上一镜像和上一版本配置；
- 变更窗口、回滚审批、上线检查单。

#### 备份与恢复

- RDS 自动备份 + 日志备份 + PITR；
- Redis AOF/RDB；
- OSS 版本控制 + 生命周期；
- 每日恢复演练；
- RPO ≤ 5 分钟、RTO ≤ 30 分钟。

### 5.7 AI 与 RAG 平台化

- 云端 LLM 为主，本地模型降级；
- 模型路由：小模型处理意图/摘要/偏好，大模型处理复杂对话；
- token 限额：每用户每日配额、单请求 max_tokens；
- QA 缓存：精确 + 语义缓存，命中率指标；
- 知识库：采集/清洗/分块/向量化/检索/精排/热更新；
- RAG 评测集：≥200 条，意图准确率 ≥90%；
- LLM 成本看板：输入/输出 token、调用次数、成本；
- 对话数据保留策略和遗忘权；
- 客服人工转接和 Agent 审查（Compliance）保持。

### 5.8 前端与客服工作台

- 管理后台按权限码渲染菜单/按钮；
- 商城自动携带 token，WebSocket 生产强制认证；
- 客服工作台：实时会话、工单、快捷回复、历史检索；
- 前端错误监控、性能监控、离线提示；
- 商城浏览器兼容、移动端适配、无障碍基础。

## 7. 里程碑与 Go/No-Go

| 里程碑 | 时间 | 关键结果 | Go 条件 |
|---|---|---|---|
| M0 | 第 1 周 | 治理与 NFR 完成 | Git/CI/Secret/ADR 可用 |
| M1 | 第 4 周 | 异步数据层 + 测试基础 | 覆盖率、迁移、集成测试通过 |
| M2 | 第 8 周 | 业务正确性 + 真实支付/物流 | 500 并发无超卖，支付退款对账一致 |
| M3 | 第 12 周 | 1000 QPS / 2000 WS / 高可用 | 压测与故障演练通过 |
| M4 | 第 15 周 | 安全与合规 | 渗透、权限、PII、等保自查通过 |
| M5 | 第 17 周 | 生产上线 | 发布、回滚、监控、值班就绪 |

Go/No-Go 检查项：

- 安全高危清零；
- 权限矩阵通过；
- 数据恢复演练通过；
- 压测达标；
- 真实支付对账通过；
- 监控告警正常；
- 回滚演练通过；
- 合规自查通过；
- 业务负责人书面确认。

## 8. 测试与质量体系

### 8.1 测试分层

| 层级 | 范围 | 工具 |
|---|---|---|
| 单元测试 | 工具、Agent、状态机、权限、计算逻辑 | pytest |
| 服务层测试 | Order/Payment/Inventory/Coupon/Refund | pytest + SQLAlchemy fixture |
| API 集成测试 | 登录、下单、支付、退款、越权 | FastAPI TestClient + testcontainers |
| 端到端测试 | 商城下单 -> 支付 -> 发货 -> 客服 -> 退款 | Playwright/Cypress（可选） |
| 性能测试 | 1000 QPS、500 并发下单、2000 WS | Locust/k6 |
| 混沌测试 | Redis 断连、Pod 被杀、DB 主从切换 | Chaos Mesh（可选） |

### 8.2 质量门禁

- `ruff` / `mypy`；
- `pytest` 全量；
- 覆盖率 ≥70%；
- `compileall`；
- 前端 `vitest` + 构建；
- 关键接口性能回归；
- Alembic 迁移检查；
- 安全扫描（SAST/依赖扫描）；
- PR 必须通过全部门禁。

## 10. 组织、流程与治理

### 10.1 角色

| 角色 | 职责 |
|---|---|
| 项目负责人 | 范围、进度、资源、验收 |
| 后端负责人 | 数据层、业务正确性、事件 |
| 前端负责人 | 商城、后台、客服工作台 |
| 安全/DevSecOps | 安全、合规、CI/CD、云 |
| 测试负责人 | 测试策略、覆盖率、压测 |
| 数据/合规负责人 | PII、隐私、等保、审计 |

### 10.2 流程

- 技术方案先写 ADR；
- 核心修改先写测试；
- 所有变更走 PR + Code Review；
- 数据库变更必须附带迁移和回滚方案；
- 上线前有 check-list 和回滚预案；
- 每周复盘安全、性能、成本、故障；
- 生产变更记录、事件记录、审计记录齐全。

## 11. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 同步转异步改动面大 | 回归 | 模块冻结、分批迁移、测试门禁 |
| 支付/退款不一致 | 资损 | 单事务 + outbox + 对账 + 幂等 |
| 库存并发 | 超卖 | 原子条件更新 + 压测 + 监控 |
| LLM 成本失控 | 运营成本 | 配额、缓存、成本看板、模型分级 |
| 数据合规 | 监管/诉讼 | 隐私基线、数据字典、删除演练 |
| 安全漏洞 | 数据泄露 | 渗透测试、依赖扫描、权限矩阵 |
| 范围蔓延 | 无法交付 | 明确不做微服务/多地域/多租户 |
| 团队人力不足 | 延期 | 按里程碑拆分，优先 P0/P1/P2 |
| 云资源成本 | 预算超支 | 压测后定规格、按 PA 折扣申请 |

## 12. 最终交付定义

项目达到 L2 标准时，应具备：

- 10 万 DAU、1000 QPS、99.9% 可用性；
- 完整商城、管理后台、客服 Agent、工单；
- 真实支付/物流（至少一种渠道）；
- 资金、库存、订单、优惠券全链路可对账；
- 全异步数据访问和事件 outbox；
- 完整 RBAC、审计、PII 加密、隐私权；
- 生产级 CI/CD、监控、告警、备份、恢复、回滚；
- 服务层覆盖率 ≥70%，关键路径集成测试通过；
- PIPL 合规和等保三级自查证据；
- 操作手册、运行手册、应急手册；
- 上线检查单和持续复盘机制。

## 13. 下一步执行建议

1. 按本方案冻结 L2 目标和 NFR；
2. 初始化 Git 仓库、分支模型、CI、ADR；
3. 先完成 P0 + P1，形成稳定的工程和测试基础；
4. 再推进 P2 业务正确性，避免在未测试的状态下接入真实支付；
5. 以压测和故障演练作为进入生产前的强制门禁；
6. 上线前完成安全、合规、回滚、备份四类演练；
7. 上线后 1 个月内复盘一次，决定是否扩展到 L3。
